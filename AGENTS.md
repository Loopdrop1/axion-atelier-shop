# AXION architecture

- Keep brand, contact, launch, VAT, fulfilment and feature settings in `src/config/shop.ts` so client-confirmed values have one source.
- UI reads commerce data only through async exports from `src/lib/commerce/index.ts`; the catalogue comes from Supabase via `source.ts` (cached 30 s on the server), so page components never query tables directly.
- Commerce contracts live in `types.ts`, the Supabase row mapping in `mapping.ts`, and image metadata in `media.ts` to separate contracts from content.
- Store only variant identifiers/quantities and wishlist product handles in persisted Zustand stores; resolve all display data through the commerce adapter.
- Hydrate persisted stores after mounting, never during SSR, to keep server and browser output consistent.
- Use TanStack Query for initial catalogue reads and route loaders, and leaf-specific German metadata for every content route.
- Keep shared presentation in `src/components/shop`; lazily import the Three scene (3D logo in the brand section further down the home page, `brand-moment.tsx`) only after section visibility and browser capability checks.
- Home motion is CSS-first in the «Motion» block at the end of `src/styles.css` (hero settle and line reveal, scroll-timeline parallax under `@supports`, `reveal-image` curtain, staggered `.product-grid` inside `Reveal`); the card → product image flight is a View Transition named only on the clicked card (`vt-product-image`, names must stay unique).
- Motion respects reduced-motion preferences; the brand section shows the exact flat SVG when animation/WebGL is unavailable and pauses its canvas offscreen.
- The hero is a full-bleed photo (eager, high fetch priority) with an optional muted loop video from `site-media` (MP4/WebM up to 25 MB): `video` for computers and tablets, `video_mobile` (portrait) for phones; a phone without its own video shows the photo. The video loads only in the browser, never with reduced motion or data saver, pauses offscreen and has a pause/play button (WCAG 2.2.2). The photo stays underneath as fallback.
- Product page: three columns on desktop (text left, images centre, buy box right; text and buy box sticky), two on tablets, stacked on phones. Details come from `origin_*` and `features_*` (one feature per line, parsed by `featureList`); 2 or fewer in stock of the chosen size shows a hint (persistent `role="status"` region). Page changes use View Transitions only when the path changes (`defaultViewTransition` types in `src/router.tsx`; search and filter navigations also pass `viewTransition: false`; off with reduced motion).
- Sample range: 52 products in nine categories tagged `muster` (card badge «Muster», notice on the product page) with illustrations from `src/assets/muster`, referenced as `asset:muster/<handle>-1|2` (category images too, `-1`). Axion is off-the-rack luxury retail: no tailoring, alterations or appointments in copy. `supabase/seed.sql` (local database, tests) and `supabase/demo/muster-einspielen.sql` (Cloud, to present the shop) hold the same products; `supabase/demo/muster-entfernen.sql` removes them before launch, clears the drawings as category images and switches off categories without active products (the admin shows a «Muster» badge and a checkbox to keep a piece; demo sizes and images only attach to products tagged `muster`; `supabase/tests/demo-scripts.test.ts` runs both scripts on a fresh database). After changing the seed run `bun scripts/db/gen-sample-catalog.ts` (after `bun run db:reset`) to regenerate `src/lib/commerce/sample-catalog.ts` (loaded lazily by `source.ts`, only without a backend, so the live shop never downloads it).
- `launched` controls metadata; after changing it regenerate `public/robots.txt` using `bun scripts/sync-robots.ts` before publishing so both protections stay aligned.
- SEO/GEO: after launch `robots.txt` allows public pages and keeps private ones disallowed (account, cart, order status, confirmation links, search, admin; list in `scripts/sync-robots.ts`); `/sitemap.xml` and `/llms.txt` (summary for AI search, `src/lib/seo/llms.ts`) are server routes, `/llms.txt` returns 404 before launch. Structured data lives in `src/lib/seo/structured.ts` (Organization and WebSite search on the home page, BreadcrumbList on collections and products, FAQPage from `pages.ts` without questions that still contain placeholders); products add brand, sku, colour, material and the return policy (`returnDays`).
- Checkout always goes through the `checkout` Edge Function (stock reservation, Stripe Checkout); never hardcode payment links in the UI.
- Admin lives under `/admin` (role `admin` in `user_roles`); stock changes only via the `admin_adjust_stock` RPC, never by updating `product_variants.stock`.
- Edge Functions: see `supabase/functions/README.md`; secrets live in Cloud, never in the repo.
- The root `README.md` is a short overview; the outdated first brief (no backend, sample data) lives in `docs/brief-v1.md`. This file, `docs/DEPLOYMENT.md` and `supabase/functions/README.md` describe the current shop.
- Backend is Lovable Cloud (region Europe). Migrations in `supabase/migrations/` are applied manually in order (Lovable does not run migration files from Git); never edit an applied migration, add a new one instead.
- Never edit the generated `src/integrations/supabase/client.ts`; `backendConfigured` and `supabaseUrl` live in `src/lib/backend.ts`.
- What runs in Cloud is `drizzle/migrations/` (written by Lovable's migration tool when Cloud was connected; same SQL as `supabase/migrations/` except `citext` → `text` with unique `lower(...)` indexes). `supabase/migrations/` stays the source for the local test database. A schema change needs a new file in both, applied once in Cloud.
- `supabase/config.toml` must keep `verify_jwt = false` for every function (they check callers themselves); Lovable dropped it once when connecting Cloud. Check it after Cloud changes and redeploy the functions if it was missing.
- Cloud lacks `citext` and rejects `INSERT INTO storage.buckets`: use text with a unique index on `lower(...)`; create buckets with the storage tool, their policies in a migration.
- The delivery area is the `SHIPPING_COUNTRIES` secret (default `CH`); adding `LI` requires the Liechtenstein clauses in the legal texts.
- English follows German in the admin: on save, `src/lib/admin/auto-translate.ts` fills empty English and re-translates machine English when the German changes, through `admin-actions` (`translate`, Lovable AI gateway, 500 requests per admin and day). Provenance is stored per field (`en_auto` columns on products, categories and product_images; `en_auto` list in `site_content` blocks; `auto` flag on announcement items and size-guide texts). English written or edited by hand is never overwritten or cleared; emptying an English field asks for a new translation. A failed translation clears only outdated machine English, so the shop shows German there.
- The complete outfit on the product page and the home look (buy the look next to the image: choose sizes, whole look or a selection into the cart) share `src/components/shop/outfit.ts`: available pieces are preselected, sold-out pieces cannot be chosen, nothing goes into the cart while a selected piece lacks an available size. Reset by remounting with `key={outfitKey(...)}`, so refetched identical data keeps the chosen sizes.
- Load budget: the Supabase client (`src/lib/supabase-client.ts` → `getSupabase()`), sonner, the page texts in `src/content/pages*.ts` and the cart/menu/search panels (`shell-overlays.tsx`, mounted after idle or on first open) are separate chunks; keep them out of static imports of the shell, `start.ts`, route `head`/`loader` code and shared lib modules (route `head` uses `content-meta.ts`, not `content.tsx`). Both web fonts are preloaded as Latin subset only (`__root.tsx`) and `styles.css` defines metric-adjusted fallbacks («Inter Fallback», «Jost Fallback») so the font swap causes no layout shift; the first product card of a grid/gallery gets `priority` (fetchpriority high).
- Home order: full-bleed hero, new arrivals as a grid right after it (8 newest tagged `neu`, 6 on tablets), category row (Embla, arrows from tablets up, swipe on phones), look, occasions, brand section, benefits, story. Desktop nav: «Neu», «Kollektion» popover (all active categories plus «Alle Stücke»), «Anlässe» popover, «Sale»; the phone menu lists everything.
- One size: a product whose only variant is named «One Size» (also «Einheitsgrösse», «OS»; `src/lib/commerce/one-size.ts`, same rule in `supabase/functions/_shared/size.ts` for mails and Stripe) has nothing to choose: preselected on the product page, card quick-add and outfits, shown as «Einheitsgrösse» / «One size» in the language of the page or order (never «Grösse One Size»; a parity test in `one-size.test.ts` keeps both rules equal). A single real size (a shoe left only in 42) is still chosen by the customer.
- Menus come from the active categories (`navQuery`); size charts from `site_content` key `size_guides` (Admin → Grössentabellen); shipping texts from `shop_settings` via `shippingLabel`; never hardcode «Gratisversand» in new UI.
- Legal and help pages exist in German (`pages.ts`) and English (`pages-en.ts`) with the same structure (a test enforces it); German is binding.
- Search is local first (`src/lib/commerce/smart-search.ts`, used by `searchCatalog`): DE/EN synonyms, typo tolerance, compounds, colour groups, category, occasion, fit, price, size, sale/new/gift intents, relevance ranking, step-wise relaxing and «Meintest du». The overlay shows understood terms, categories and popular/recent searches (`recent-searches.ts`, browser only); the search page lets shoppers remove understood terms and, for sentences of three or more words the local parser does not fully understand, asks the `search-assist` Edge Function (AI, rate-limited, whitelist-sanitised, cached per session).
- Back-in-stock alerts: sold-out sizes on the product page offer «Benachrichtigen» (`stock-alert-form.tsx` → `stock-alert` Edge Function, double opt-in, confirm page `/benachrichtigung/bestaetigen`); restocking a size from 0 in the admin stock dialog or by booking in a return (`admin_restock_order` answers `back_in_stock` with the variants that went from 0 to more) calls `admin-actions` `notify_restock`, which marks only sent mails as notified and removes the address. Table `stock_alerts` (admin read only), RPCs for `service_role` only.
- The contact form posts to the `contact` Edge Function (`contact_guard`: 5 per IP or IPv6 /64 and 3 per address per hour, 20 per hour and 50 per day for everyone; messages are not stored, rate-limit keys only as hashes); all functions require `Content-Type: application/json` (415 otherwise). The admin order page prints a receipt (`components/admin/receipt.tsx`, named print page `receipt`).

- Search serialization uses plain string query values, with optional defaults resolved by consumers, to avoid redirecting clean URLs.
- Shared Dialog panels restore their external opener and initialise search focus; filter and occasion dropdowns use controlled non-modal Radix Popovers for keyboard and outside-click handling.
- Reveal visibility is controlled by the pre-paint html.js class and CSS reduced-motion media queries, so SSR content remains visible without JavaScript.
- Persisted-store screens await hydration and data resolution before showing an empty state, to prevent false empty flashes.
- Leaf metadata uses the configured site URL for canonical and structured-image URLs, keeping deployment-specific values centralised.
- Missing catalogue/product records use a leaf not-found component so their metadata executes alongside HTTP 404 rendering.
- Store client legal/help copy as structured page data in `src/content/pages.ts`; the shared renderer interpolates config values and detects placeholders at render time so content and draft status stay aligned.

- Operations: `client-error` Edge Function + table `client_errors` collect technical browser errors without personal data (path without query, stack, user agent, release; count per fingerprint within 24 h; deleted after 30 days inside `client_error_report`; admins read/delete via RLS, page `/admin/fehler`). The browser reporter `src/lib/client-errors.ts` stays tiny (no static Supabase import), installs after idle from the shell, sends at most 5 per page view, never in dev or without backend. `/api/health` (server route, `src/lib/health.ts`) answers `{ok, catalogue, time}` with `no-store` for uptime monitoring and is disallowed in `robots.txt`. `admin-actions` `system_status` returns only booleans plus the Stripe mode for the admin dashboard checklist «Bereit für den Livegang» (`components/admin/readiness.tsx`); never return secret values. Runbooks: `docs/BETRIEB.md`, `docs/TESTKAUF.md`, `docs/IPHONE-CHECK.md`.
- Customer returns: public form `/retoure` (`return-form.tsx`, noindex and in `robots.txt`; account order detail links to it with `?order=`) → `return-request` Edge Function (`lookup` by order number + email, `submit` with items, quantities and reason; uniform `NOT_FOUND`; window = `SHOP_RETURN_DAYS` from `shipped_at`, else `paid_at`; no label or cost promise in copy or mail) → table `return_requests` (requested → received → refunded/rejected; RLS admin only, RPCs `service_role` only, migration `0016`); admin page `/admin/retouren` shows them, refund and «Retoure einbuchen» stay on the order. Reasons live in `supabase/functions/_shared/returns.ts` and `src/lib/returns.ts` (parity test).
- Marketing: `/feeds/google.xml` (RSS 2.0 mit `g:`, ein Eintrag pro Grösse, ohne `muster`; `src/lib/feeds/google.ts`) ist vor `launched` 404 und dient Google Merchant Center und Meta; `shopConfig.analytics.plausibleDomain` (Plausible, leer = aus) und `shopConfig.verification` (Search Console, Bing) werden nur über `src/lib/marketing.ts` in den `<head>` gesetzt (Skript nur mit `launched`, nie im Admin/Dev); der Datenschutz-Punkt mit `{{analytics}}` erscheint nur bei gesetzter Domain; Ereignisse über `trackEvent` (`src/lib/analytics.ts`). Anleitung: `docs/MARKETING.md`.
- Swiss Post labels (optional, untested against the real API until Axion has a Post business account): `supabase/functions/_shared/swiss-post.ts` (OAuth client-credentials token cached until expiry, `generateAddressLabel`, one retry on 401 and on transient errors, errors mapped to `POST_*` codes) behind `admin-actions` `post_label` (paid cart orders to CH/LI only; returns `identCode` + PDF, never marks shipped: the admin page prefills the tracking field and the existing «Versendet» action sends the mail). Secrets `POST_CLIENT_ID`, `POST_CLIENT_SECRET`, `POST_FRANKING_LICENSE` (+ `POST_PRODUCT` ECO/PRI); without them `POST_NOT_CONFIGURED` and the admin button is disabled; `system_status` exposes only the boolean `swissPost` (optional row in the readiness checklist). Sender comes from `SHOP_NAME` + `SHOP_ADDRESS` («Strasse Nr, PLZ Ort»).
- Low-stock alert to the shop: stock is decremented at reservation (`reserve_checkout`), but `stripe-webhook` calls `sendLowStockAlert` (`order-mail.ts`, RPC `low_stock_after_order`, migration `20261029001800`/Cloud `0017`) only on a newly paid order, for variants that crossed `LOW_STOCK_THRESHOLD` (secret, default 2) with this order; one mail per order (Resend key `order-<id>-lowstock`), never throws into the webhook.
